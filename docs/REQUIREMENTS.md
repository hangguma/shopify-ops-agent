## 1. 목적

한 사람이 Shopify 스토어를 운영할 수 있도록, AI 에이전트가 **운영 데이터를 분석하고 스토어를 셋업·변경하는 일**을 대신하는 시스템을 만든다.

핵심 원칙은 하나다. **LLM은 제안하고, 사람은 승인하고, 쓰기는 결정론적 코드가 한다.** 에이전트가 스토어를 직접 바꾸는 경로는 두지 않는다.

### 1.1 배경

- 소규모 D2C 운영자는 상품 등록, 재고 점검, 페이지·메뉴 관리 같은 반복 작업에 시간을 쓴다.
- 기존 도구는 한 구간만 자동화한다(광고, 결제 이후 물류 등). 여러 구간을 하나의 에이전트 시스템으로 묶은 1인용 도구는 드물다.
- SFCC는 개인 개발 환경이 없어, 무료 Shopify Partner 개발 스토어를 기반으로 한다.

### 1.2 성공 기준

| ID | 기준 | 측정 방법 |
|---|---|---|
| SC-1 | 실제 dev 스토어 데이터로 운영 보고서가 끝까지 생성된다 | UAT TC-01 |
| SC-2 | 브랜드 브리프 하나로 컬렉션·상품·페이지·메뉴가 갖춰진 스토어가 열린다 | UAT TC-13 |
| SC-3 | 사람이 승인하지 않은 변경은 스토어에 한 건도 반영되지 않는다 | 자동 T-45, UAT TC-11 |
| SC-4 | 같은 계획을 다시 적용해도 중복 리소스가 생기지 않는다 | 자동 T-46, UAT TC-14 |
| SC-5 | 모든 쓰기 시도가 결과와 함께 기록된다 | 자동 T-50 |

## 2. 사용자와 범위

### 2.1 사용자

| 사용자 | 설명 | 주요 목표 |
|---|---|---|
| 운영자 (Primary) | 혼자 또는 소규모로 Shopify 스토어를 운영하는 사람 | 반복 운영 작업을 맡기고, 판단이 필요한 지점만 승인 |
| 개발자 | 이 시스템을 확장·유지보수하는 사람 | 에이전트·도구를 추가해도 안전 장치가 유지되는 구조 |

### 2.2 범위 (Phase별)

| Phase | 상태 | 범위 |
|---|---|---|
| 1 | ✅ 완료 | 읽기 전용 분석: 상품·재고·주문 조회 → 품절 위험·저성과 상품 보고서 |
| 2A | ✅ 구현 (PR #1, live 검증 전) | 스토어 셋업: 브리프 → StorePlan → 승인 → Online Store 적용 |
| 2B | 계획 | 헤드리스 storefront (Hydrogen 또는 Next.js + Storefront API) |
| 2C | 계획 | 운영 executor (가격·재고 변경) + Streamlit 승인 UI |
| 3 | 계획 (stretch) | 정기 모니터링 + 알림 |

### 2.3 범위 밖 (현재)

- 결제, 환불, 고객 개인정보 수정
- 광고 집행(Meta/Google 등 외부 채널)
- 상품 이미지 생성·업로드, 멀티 variant 상품, 테마 코드 편집 (2A 기준)
- 운영 중인 실 스토어 대상 실행 (dev 스토어에서 검증 후 별도 결정)

## 4. 비기능 요구사항

| ID | 분류 | 요구사항 | 현재 충족 방식 |
|---|---|---|---|
| NFR-1 | 안전 | LLM에는 쓰기 도구를 주지 않는다. 쓰기는 사람이 승인한 항목에 한해 결정론적 코드만 수행한다 | Builder·Analyst는 읽기 도구만 보유, 쓰기 함수는 Executor만 호출 |
| NFR-2 | 안전 | 쓰기 작업의 기본 모드는 dry run이다 | `apply`에 `--execute`가 없으면 dry run |
| NFR-3 | 신뢰성 | Shopify의 `userErrors`(200 응답 내 실패)를 성공으로 오인하지 않는다 | `_raise_user_errors` |
| NFR-4 | 신뢰성 | 재실행에 안전하다 (멱등성) | handle 기반 조회 후 생성, `productSet` upsert |
| NFR-5 | 추적성 | 모든 쓰기 시도는 시각·대상·결과와 함께 append-only 로그에 남는다 | `outputs/audit_log.jsonl` |
| NFR-6 | 보안 | API 키·시크릿은 코드와 git에 넣지 않는다 | `.env` + `.gitignore`, 토큰은 런타임 발급·메모리 캐시 |
| NFR-7 | 보안 | 앱 scope는 phase에 필요한 최소한만 부여한다 | Phase 1은 읽기 3종, 2A에서 쓰기 6종 추가 |
| NFR-8 | 테스트 가능성 | 내부 로직은 네트워크·키 없이 테스트한다 | 61개 단위 테스트 전부 mock |
| NFR-9 | 성능 | 분석 1회는 상품·주문 20개 기준 60초 이내 | UAT TC-08 (측정 전) |
| NFR-10 | 비용 | 분석 1회 LLM 비용은 소액(약 $0.05 이하)을 목표로 한다 | UAT TC-09 (측정 전), `max_iter` 제한 |
| NFR-11 | 유지보수 | 에이전트 간 입출력은 Pydantic 계약으로 고정한다 | `AnalysisReport`, `StorePlan` |
| NFR-12 | 이식성 | Shopify API 버전은 설정값으로 관리한다 | `SHOPIFY_API_VERSION` (기본 2026-04) |

## 5. 제약과 가정

| 구분 | 내용 |
|---|---|
| 플랫폼 | Shopify Partner 개발 스토어 (무료, 비밀번호 보호, 실결제 불가) |
| 인증 | Dev Dashboard 앱의 client credentials grant. 정적 admin 토큰 없음, 토큰 약 24시간 만료 |
| 앱 배포 | custom distribution (주문 데이터 접근 위해 선택, 비가역) |
| API | Admin GraphQL API (2026-04). 2B부터 Storefront API 추가 |
| LLM | Anthropic Claude (기본 `anthropic/claude-sonnet-5`), CrewAI + LiteLLM 경유 |
| 런타임 | Python 3.10+ (3.13에서 테스트), 로컬 CLI |
| 가정 | dev 스토어에 Online Store 채널과 `main-menu`가 있다 |

## 6. 위험

| ID | 위험 | 영향 | 대응 |
|---|---|---|---|
| R-1 | LLM이 브리프에 없는 주장(효능, 인증)을 상품 설명에 넣음 | 허위 표시 | 프롬프트 금지 규칙 + 사람 리뷰 + 계획 파일 직접 수정 가능 |
| R-2 | 쓰기 scope 누락으로 적용 중간 실패 | 부분 적용 | 항목별 오류 기록, 실패해도 계속, 재실행 시 멱등 |
| R-3 | Shopify API 버전 변경으로 mutation 형태가 바뀜 | 쓰기 실패 | API 버전 고정, 쓰기 레이어를 한 모듈에 격리 |
| R-4 | `productSet`의 목록 필드(컬렉션)가 전체 교체 방식이라 스토어에서 수동 추가한 컬렉션 연결이 사라짐 | 데이터 손실 | 문서화, 2C에서 병합 옵션 검토 |
| R-5 | CrewAI 응답이 thinking에서 잘려 빈 응답 | 실행 실패 | `max_tokens=16384` (Phase 1 E-6에서 진단·해결) |
| R-6 | 메뉴 교체가 기존 메뉴 항목을 덮어씀 | 탐색 구조 손실 | 메뉴는 별도 승인 항목, dry run에서 결과 항목 수 표시 |
